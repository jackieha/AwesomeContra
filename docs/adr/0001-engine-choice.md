# ADR 0001：自研 Canvas 2D 引擎，不使用 Cocos / LayaAir / Egret

- **状态**：已采纳
- **日期**：2026-08-28
- **背景 issue**：LEDA-1（整体方案）、LEDA-2（本决策落库）
- **相关**：`docs/adr/0002-minigame-vs-miniprogram.md`

## 背景

AwesomeContra 是一款横版跑射像素动作游戏，主形态为微信小游戏（详见 `docs/design.md`）。项目**全程由 agent 以纯文本代码方式推进**，并要求有可在 CI 中自动运行的回归测试。

微信小游戏生态里有成熟的引擎选项：Cocos Creator、LayaAir、Egret，以及若干轻量 2D 库。需要决定是采用其中之一，还是自研。

## 决策

**自研极简 Canvas 2D 引擎，零运行时依赖。**

引擎内核放在 `engine/`，不含任何游戏规则，也不引用任何宿主 API；能力包括：固定步长主循环、Canvas 2D 渲染抽象（图集 + 整数缩放 + 批量 `drawImage`）、输入位掩码抽象、资源加载、音频抽象、对象池、显式播种 PRNG。规模预期在 1500 行以内。

## 理由

### 1. 确定性定步长模拟是硬需求，而它必须由自己掌控（决定性因素）

`docs/design.md` §9.2 把「确定性输入回放」作为**唯一能自动捕获手感回归的机制**。要成立，需要同时满足：固定 1/60 步长、唯一且显式播种的随机源、不读挂钟时间、碰撞求解顺序固定、实体遍历顺序稳定。

商业引擎的主循环普遍以 `dt` 变步长驱动，内部有自己的调度器、缓动系统、粒子系统与动画组件，其中任何一处引入 `Math.random()`、`Date.now()` 或依赖对象键序的遍历，都会让回放不可复现——而且**很难证明它没有引入**。要在这类引擎上建立确定性，实际工作量是审计并绕开引擎的大半个运行时，成本高于自己写一个。

这是本决策中唯一无法用「引擎也能做到」反驳的一条，因此权重最高。

### 2. agent 驱动的开发需要一切都是可 diff 的文本

编辑器驱动的工程会产出 `.scene` / `.prefab` / `.fire` 等序列化文件与 GUI 建立的资源绑定关系。这些文件：

- 体积大、格式冗长，一个微小改动产生大片 diff，code review 失效；
- 含自动生成的 UUID 与引用关系，手工编辑容易产生悬空引用，而错误在运行时才暴露；
- 部分为二进制或半二进制，无法可靠地增量修改。

agent 的核心工作方式是读写文本并 review diff。让工程状态的一部分脱离这个回路，等于让那一部分脱离质量控制。

### 3. 本项目不需要商业引擎的任何重型能力

清点一下实际用到的：AABB 碰撞、逐帧精灵动画、单图集绘制、音频播放、触摸输入。都不超过几十行到几百行。

而商业引擎的价值集中在：3D、刚体物理、骨骼动画、粒子编辑器、UI 布局系统、场景编辑器、可视化动画状态机。本项目一个都不用。引入它们不是「用不上就不管」——它们会带来包体、启动开销，以及一整套需要理解才能调试的不可控行为。

### 4. 零运行时依赖对包体预算有实质帮助

主包目标 ≤2MB（`docs/design.md` §8）。零依赖让这个预算几乎全部留给代码与首关图集。

### 5. 宿主抽象只有自己写才能真正干净

要同时支持小游戏与 H5 两个宿主（`docs/design.md` §2），需要一个窄且明确的 adapter 边界。商业引擎自带跨平台适配层，但那层是为它自己的架构设计的，不一定覆盖我们要的组合，也不便于按我们的需要增删宿主。自研时 adapter 契约是我们定义的，`tools/lint-no-host-api.js` 能静态强制它。

## 被否方案

### Cocos Creator（被否）

**优点**：小游戏生态里最成熟，文档与真机适配案例最多，编辑器出关卡快，社区解决方案多。

**否决理由**：编辑器驱动的工程形态与理由 2 直接冲突——场景与预制体是 agent 无法可靠维护的工程状态。此外其运行时体量与调度器架构与理由 1 的确定性要求冲突。这两条都不是可以靠工程纪律绕过的，是形态层面的不匹配。

若本项目由人类团队在编辑器里推进，Cocos Creator 会是合理甚至更优的选择——**这个决策的前提是执行者是 agent，前提变了应重新评估。**

### LayaAir（被否）

**优点**：2D 性能口碑好，对小游戏包体较友好，有代码优先的使用方式。

**否决理由**：仍是编辑器 + IDE 中心的工作流，工程结构里有生成物；且要建立确定性仍需审计其运行时。相对 Cocos 的生态劣势又让「遇到坑时能找到答案」这一优点缩水。收益不足以抵消理由 1 与 2。

### Egret（被否）

**优点**：轻量，TypeScript 优先，2D 定位契合。

**否决理由**：生态活跃度与维护力度是最大风险——一个引擎级依赖在项目中期停止维护，代价远超自研 1500 行内核。且它带来的抽象（显示列表、事件系统）与我们需要的「零堆分配、定步长、扁平实体数组」写法方向相反，会持续产生摩擦。

### 通用轻量 2D 库（PixiJS 等，被否）

**优点**：只做渲染，抽象干净，性能好。

**否决理由**：包体（几百 KB 级）换来的是我们不需要的通用性（WebGL 抽象、滤镜、显示树）。本项目只用单图集 + Canvas 2D 的整数缩放绘制，自己写不到 300 行且完全可控。此外其显示树的绘制顺序与我们的绘制批次控制会互相干扰。

## 后果

**接受的成本**：

- 需要自己写并维护主循环、渲染、输入、音频、资源加载、对象池——约 1500 行，是 Stage 1 的主要工作量（Step 3 / LEDA-4）。
- 没有场景编辑器，关卡靠手写 JSON + `tools/validate-level.js` 校验。这需要校验器足够严格才不至于沦为盲写（因此 `docs/formats.md` §1.5 把可通关性检查列为必需项）。
- 真机兼容性问题需要自己排查，没有引擎社区的现成答案。
- 音频是自研成本最高的部分（各宿主音频行为差异大、移动端自动播放限制多），需要预留缓冲。

**获得的收益**：

- 确定性回放可以成立，从而 CI 能自动捕获手感回归。
- 全部工程状态是可 review 的文本。
- 零运行时依赖，包体预算充裕。
- 「每帧零堆分配」这类硬性能规则可以真正落实（`docs/design.md` §8），因为每一行分配都在自己代码里。

**重新评估的触发条件**：如果项目后续引入需要骨骼动画、复杂 UI 布局或 3D 的内容，或执行者从 agent 转为人类编辑器团队，本决策应重新评估。
