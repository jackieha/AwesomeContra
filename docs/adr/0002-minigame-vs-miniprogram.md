# ADR 0002：以微信小游戏为唯一发布形态

- **状态**：已采纳。形态已由项目方于 2026-08-28 在 LEDA-2 上明确确认（「就是微信小游戏。」），本 ADR 的原开放问题随之关闭。
- **日期**：2026-08-28（同日据项目方确认修订）
- **背景 issue**：LEDA-1（整体方案）、LEDA-2（本决策落库与确认）
- **相关**：`docs/adr/0001-engine-choice.md`

## 背景

项目目标的原始表述是「参考魂斗罗经典游戏，实现一个**微信小程序**的版本」。「小程序」一词在微信生态里有歧义——它既可指普通小程序，也常被用来泛指「微信里的轻应用」，而后者包含小游戏。

微信平台上有两种可承载游戏的形态，二者是不同的账号类目与不同的运行时：

| | 普通小程序 | 小游戏 |
|---|---|---|
| 入口 | `app.js` + 页面（WXML/WXSS/JS） | `game.js`，无页面层 |
| 画布 | `<canvas type="2d">` 组件 | `wx.createCanvas()` |
| 架构 | 逻辑层（JSCore）与渲染层（WebView）分离，通过 setData 通信 | 单一 JS 环境，直接持有 canvas |
| 帧循环 | 组件内 `canvas.requestAnimationFrame` | 全局 `requestAnimationFrame` |
| 横屏 | 需页面配置，能力受限 | `game.json` 内 `deviceOrientation: "landscape"` |
| 账号类目 | 小程序 | **小游戏（需游戏类目资质）** |

本 ADR 初版（同日早些时候）选择小游戏为主形态，但因为无法单方面确定项目方的账号类目情况，额外把「普通小程序宿主随时可追加」做成了架构级保障。**项目方随后确认目标形态就是微信小游戏**，该歧义消除，对冲不再需要。

## 决策

**微信小游戏是唯一的发布形态。不再计划普通小程序宿主。**

具体做法：

1. `engine/` 与 `game/` 中**不允许出现任何 `wx.` 前缀标识符**，也不允许直接触碰 `document` / `window`。所有宿主能力经 platform adapter 注入（契约见 `docs/design.md` §2.3）。
2. `tools/lint-no-host-api.js` 在 CI 中静态检查这条约束，违反即构建失败。
3. 宿主只有两个：`platform/wx-minigame/`（发布形态）与 `platform/web/`（开发、单测、Playwright、CI）。**不创建 `platform/wx-miniprogram/` 预留目录。**

第 1、2 条**不因本次确认而放松**。它们的正当性从来主要来自 H5 宿主：确定性回放、单元测试与 Playwright 截图都跑在 web 宿主上（`docs/design.md` §9、ADR 0001 §1），玩法层若耦合 `wx.*` 就无法在 Node 与浏览器里测试。换言之，adapter 边界是**测试基建的前提**，不是为小程序宿主留的后门——去掉第三个宿主并不削弱它。

## 理由

### 1. 动作射击的帧率与输入延迟要求，普通小程序架构满足不了

跑射游戏对帧时间抖动极其敏感：玩家一击死，一次 100ms 的卡顿可以直接造成非玩家过失的死亡。

普通小程序的逻辑层与渲染层是两个环境，中间隔着序列化通信。虽然 `<canvas type="2d">` 通过 `canvas.requestAnimationFrame` 减少了这层开销，但触摸事件仍要跨层送达逻辑层，帧循环也受组件生命周期与页面调度影响。**这条链路上的抖动不在我们的控制范围内**，无论怎样优化代码都无法保证。

小游戏形态是单一 JS 环境，直接持有 canvas，主循环由我们自己驱动——这正是 ADR 0001 里确定性定步长循环所需要的前提。

### 2. 横屏是必需的，小游戏形态对它是一等支持

逻辑分辨率 256×224 的横版卷轴必须横屏运行（`docs/design.md` §5.1）。小游戏侧一行 `deviceOrientation: "landscape"` 即可；普通小程序的横屏支持要处理页面级配置与旋转时机，是持续的麻烦源。

### 3. 形态歧义已由项目方直接消除，不需要我们替他们推断

初版 ADR 在这一点上是保守的：「小程序版本」这个措辞既可能指技术形态，也可能只是指分发渠道，而账号类目情况是我们无法单方面确定的因素，所以用架构对冲代替了猜测。

项目方已明确「就是微信小游戏」，这个开放问题关闭。**由需求方直接裁定优于我们的任何推断**，因此现在按单一形态推进，把对冲的复杂度去掉——保留一个没人打算实现的宿主，不是稳健，是未完成的设计。

### 4. 去掉未计划的宿主，消除「预留目录腐烂」

初版把 `platform/wx-miniprogram/` 列为预留目录，同时自己也指出了风险：长期不实现、不验证的预留目录只是一个假设，不是能力。既然形态已定，正确处理是删掉它，而不是留着一个永远不会被 CI 覆盖的空壳。

adapter 边界仍在，且仍有 lint 强制。若将来真的需要普通小程序宿主，它是一个受限的增量（写一个 adapter 实现，预期 200 行内），而不是重写——**这个可选性由边界本身提供，不需要一个空目录来占位。**

## 被否方案

### 只做普通小程序（被否）

**优点**：最贴合原始措辞的字面读法；不需要游戏类目资质；账号申请门槛低。

**否决理由**：理由 1 的帧率与输入延迟风险是产品级的——一个卡顿的跑射游戏不是"稍差的版本"，而是不可玩的版本。另外它也会削弱确定性循环的基础。项目方确认目标是小游戏后，本方案的唯一支撑（字面措辞）也不再成立。

### 小游戏为主形态 + 保留普通小程序宿主作为对冲（初版决策，已被本次修订取代）

**优点**：在形态归属未确定时不押注，账号类目受限时有明确降级路径。

**取代理由**：它解决的是「我们不知道项目方要哪个形态」这个信息缺口。项目方确认后缺口消失，对冲变成纯成本——第三个 adapter 实现路径、为普通小程序压包体的额外约束、以及一个长期不被验证的预留目录。**对冲在不确定时是审慎，在确定后是负债。**

### 两个形态同时作为一等公民并行开发（被否）

**优点**：两条路都不留遗憾。

**否决理由**：翻倍的真机测试矩阵与性能调优工作量，换来的是一个明确更差的版本也要达到"发布级"品质。在 MVP 阶段这是纯粹的浪费。

### 用 WebView 内嵌 H5（被否）

**优点**：一套 H5 代码通吃，开发成本最低。

**否决理由**：小程序 `web-view` 组件对个人主体不开放、需配置业务域名、无法使用小程序原生能力（分享、支付、订阅消息），且 WebView 内的性能与手感比 `<canvas type="2d">` 更不可控。同时它会让 §1 的问题变得更糟而不是更好。

## 后果

**接受的成本**：

- **游戏类目资质是发布前置条件**：小游戏必须以游戏类目的小程序账号发布。这不再是一个需要架构对冲的设计风险（形态已定），但仍是 Stage 5 发布准备的一个检查项——代码完成不等于可发布。资质与备案（含可能需要的版号，取决于是否含付费/广告等经营内容）应在 Stage 5 之前走完流程，不要等到要提审时才发现缺件。
- `engine/` 与 `game/` 里所有宿主能力都要走 adapter，写起来比直接调 `wx.*` 啰嗦一层。这是刻意的代价，由测试基建而非形态兼容性正当化。
- 主包 2MB 的目标限制了首关素材与代码规模，比小游戏平台的实际上限更紧。这是自加的首屏加载速度目标，见 `docs/design.md` §8。
- 放弃了普通小程序宿主这条已铺好的路。若形态判断将来反转，需要新写一个 adapter 实现并重新压包体——但玩法层不需要改动。

**获得的收益**：

- 发布形态在帧率、输入延迟、横屏支持上都没有架构层面的天花板。
- 只有两个宿主要维护与验证，真机测试矩阵和 CI 都更小。
- adapter 边界有 lint 强制，两个宿主共享同一套玩法代码，玩法行为逐帧一致；玩法层可在 Node 中直接单测。
- 没有未验证的预留目录假装成能力。

**重新评估的触发条件**：项目方改变形态要求；游戏类目资质确认不可得（此时降级路径是新写普通小程序 adapter，玩法层不动）；或微信平台改变两种形态的能力边界（例如普通小程序获得等价的主循环控制权）。
