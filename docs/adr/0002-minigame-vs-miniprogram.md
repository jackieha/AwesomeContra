# ADR 0002：以微信小游戏为主形态，通过 platform adapter 保留普通小程序宿主

- **状态**：已采纳
- **日期**：2026-08-28
- **背景 issue**：LEDA-1（整体方案）、LEDA-2（本决策落库）
- **相关**：`docs/adr/0001-engine-choice.md`

## 背景

项目目标的原始表述是「参考魂斗罗经典游戏，实现一个**微信小程序**的版本」。

微信平台上有两种可承载游戏的形态，二者是不同的账号类目与不同的运行时：

| | 普通小程序 | 小游戏 |
|---|---|---|
| 入口 | `app.js` + 页面（WXML/WXSS/JS） | `game.js`，无页面层 |
| 画布 | `<canvas type="2d">` 组件 | `wx.createCanvas()` |
| 架构 | 逻辑层（JSCore）与渲染层（WebView）分离，通过 setData 通信 | 单一 JS 环境，直接持有 canvas |
| 帧循环 | 组件内 `canvas.requestAnimationFrame` | 全局 `requestAnimationFrame` |
| 横屏 | 需页面配置，能力受限 | `game.json` 内 `deviceOrientation: "landscape"` |
| 账号类目 | 小程序 | **小游戏（需游戏类目资质）** |

需要在两者间做出选择，同时不违背用户「小程序版本」的字面要求。

## 决策

**主形态是微信小游戏。同时把架构约束成「核心与宿主完全解耦」，使普通小程序宿主随时可以低成本追加。**

具体做法：

1. `engine/` 与 `game/` 中**不允许出现任何 `wx.` 前缀标识符**，也不允许直接触碰 `document` / `window`。所有宿主能力经 platform adapter 注入（契约见 `docs/design.md` §2.3）。
2. `tools/lint-no-host-api.js` 在 CI 中静态检查这条约束，违反即构建失败。
3. `platform/wx-minigame/` 是发布形态；`platform/web/` 是开发与自动化形态；`platform/wx-miniprogram/` 是预留目录，Stage 5 之后按需实现。
4. 主包体积目标 ≤2MB（`docs/design.md` §8）刻意取普通小程序也能满足的量级，让备用形态在整个项目周期内保持可行——**不做这一点的话，「随时可以追加」在实现到一半时就会悄悄变成不可能。**

## 理由

### 1. 动作射击的帧率与输入延迟要求，普通小程序架构满足不了

跑射游戏对帧时间抖动极其敏感：玩家一击死，一次 100ms 的卡顿可以直接造成非玩家过失的死亡。

普通小程序的逻辑层与渲染层是两个环境，中间隔着序列化通信。虽然 `<canvas type="2d">` 通过 `canvas.requestAnimationFrame` 减少了这层开销，但触摸事件仍要跨层送达逻辑层，帧循环也受组件生命周期与页面调度影响。**这条链路上的抖动不在我们的控制范围内**，无论怎样优化代码都无法保证。

小游戏形态是单一 JS 环境，直接持有 canvas，主循环由我们自己驱动——这正是 ADR 0001 里确定性定步长循环所需要的前提。

### 2. 横屏是必需的，小游戏形态对它是一等支持

逻辑分辨率 256×224 的横版卷轴必须横屏运行（`docs/design.md` §5.1）。小游戏侧一行 `deviceOrientation: "landscape"` 即可；普通小程序的横屏支持要处理页面级配置与旋转时机，是持续的麻烦源。

### 3. 「小程序版本」的意图是「在微信里能玩」，不是形态的技术细节

小游戏在用户视角就是「微信里的小程序」——同一个下拉入口、同一个分享链路、同一套小程序码。用户提出这个要求时表达的是分发渠道，不是运行时选型。

但这里有一个**不能由我们单方面决定**的因素：小游戏需要游戏类目的账号资质，而普通小程序不需要。如果项目方手上只有普通小程序账号，或所在主体拿不到游戏类目，形态选择就被账号资质而非技术因素决定。因此本决策的第 1–4 条把「保留普通小程序宿主」做成了**架构级保障**，而不是一句口头承诺。

### 4. 保留备用形态的成本很低，事后补救的成本很高

adapter 边界是无论如何都要有的——H5 宿主（开发与 CI 所需，见 ADR 0001）已经强制我们把宿主能力抽象出来。既然 adapter 已经存在且有 lint 强制，多支持一个宿主的增量成本只是写一个 adapter 实现（预期 200 行内）。

反过来，如果一开始就让 `wx.*` 渗进玩法层，事后要剥离等于重写；而这种渗透在没有 lint 强制时几乎必然发生。

## 被否方案

### 只做普通小程序（被否）

**优点**：最贴合用户字面要求；不需要游戏类目资质；账号申请门槛低。

**否决理由**：理由 1 的帧率与输入延迟风险是产品级的——一个卡顿的跑射游戏不是"稍差的版本"，而是不可玩的版本。另外它也会削弱确定性循环的基础。

不过这个方案的**核心诉求已被本决策吸收**：架构保证它随时可做，只是不作为主形态。

### 只做小游戏，不预留小程序宿主（被否）

**优点**：最省事，不需要维护 adapter 的第三个实现路径，也不需要为普通小程序压包体。

**否决理由**：把用户明确说出的「小程序版本」这个词直接判定为不需要，是替用户做了不该我们做的决定；且资质风险（理由 3）真实存在。而保留它的成本很低（理由 4）。

### 两个形态同时作为一等公民并行开发（被否）

**优点**：两条路都不留遗憾。

**否决理由**：翻倍的真机测试矩阵与性能调优工作量，换来的是一个明确更差的版本也要达到"发布级"品质。在 MVP 阶段这是纯粹的浪费。正确的顺序是先把一个形态做好，等有明确需求（资质受限、或渠道要求）再启用备用形态。

### 用 WebView 内嵌 H5（被否）

**优点**：一套 H5 代码通吃，开发成本最低。

**否决理由**：小程序 `web-view` 组件对个人主体不开放、需配置业务域名、无法使用小程序原生能力（分享、支付、订阅消息），且 WebView 内的性能与手感比 `<canvas type="2d">` 更不可控。同时它会让 §1 的问题变得更糟而不是更好。

## 后果

**接受的成本**：

- 需要游戏类目账号资质才能发布主形态。**这是外部依赖，需在 Stage 5 之前确认**——若确认不可得，则启用普通小程序宿主并接受其帧率上限。这是本决策唯一的外部风险项，应尽早向项目方核实。
- `engine/` 与 `game/` 里所有宿主能力都要走 adapter，写起来比直接调 `wx.*` 啰嗦一层。这是刻意的代价。
- 主包 2MB 的保守目标限制了首关素材与代码规模，比小游戏平台的实际上限更紧。
- `platform/wx-miniprogram/` 长期处于未实现状态，存在"预留目录腐烂"的风险——需要在 Stage 5 至少做一次可运行验证，否则"随时可以追加"只是假设。

**获得的收益**：

- 主形态在帧率、输入延迟、横屏支持上都没有架构层面的天花板。
- adapter 边界有 lint 强制，三宿主（含 CI 用的 H5）共享同一套玩法代码，玩法行为逐帧一致。
- 账号资质风险有明确的降级路径，不会在项目后期变成死局。

**重新评估的触发条件**：游戏类目资质确认不可得；或微信平台改变两种形态的能力边界（例如普通小程序获得等价的主循环控制权）。
