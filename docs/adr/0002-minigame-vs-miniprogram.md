# ADR 0002：以微信小游戏为唯一实现形态，保留普通小程序宿主为延后选项

- **状态**：已采纳。形态与范围由项目方于 2026-08-28 在 LEDA-2 上两次确认：形态为微信小游戏（「就是微信小游戏。」）；普通小程序宿主**保留在计划中但当前不实现**（「不删除，就只做微信小游戏」）。
- **日期**：2026-08-28（同日据项目方两次确认修订）
- **背景 issue**：LEDA-1（整体方案）、LEDA-2（本决策落库与确认）
- **相关**：`docs/adr/0001-engine-choice.md`

## 背景

项目目标的原始表述是「参考魂斗罗经典游戏，实现一个**微信小程序**的版本」。「小程序」一词在微信生态里有歧义——它既可指普通小程序，也常被用来泛指「微信里的轻应用」，而后者包含小游戏。

微信平台上有两种可承载游戏的形态，二者是不同的账号类目与不同的运行时：

| | 普通小程序 | 小游戏 |
|---|---|---|
| 入口 | `app.js` + 页面（WXML/WXSS/JS） | `game.js`，无页面层 |
| 画布 | `<canvas type="2d">` 组件 | `wx.createCanvas()` |
| 架构 | 逻辑层（JSCore）与渲染层（WebView）分离，通过 setData 通信 | 单一 JS 环境，直接持有 canvas |
| 帧循环 | 组件内 `canvas.requestAnimationFrame` | 全局 `requestAnimationFrame` |
| 横屏 | 需页面配置，能力受限 | `game.json` 内 `deviceOrientation: "landscape"` |
| 账号类目 | 小程序 | **小游戏（需游戏类目资质）** |

**确认过程**（保留以说明本决策为何是现在这个形状）：

1. 本 ADR 初版选择小游戏为主形态，并因为无法单方面确定项目方的形态归属与账号类目情况，额外把「普通小程序宿主随时可追加」做成架构级保障。
2. 项目方确认形态就是微信小游戏。据此曾一度取消该对冲，并删除 `platform/wx-miniprogram/`。
3. 项目方进一步明确**不要删除**普通小程序宿主，同时**当前只做微信小游戏**。故恢复其在规划中的位置，但明确标注为延后、当前不实现。

第 3 步是本决策的最终状态：**保留选项，不实现选项。**

## 决策

**微信小游戏是当前唯一的实现与发布形态。普通小程序宿主保留在规划中，作为延后选项，本项目当前不实现。**

具体做法：

1. `engine/` 与 `game/` 中**不允许出现任何 `wx.` 前缀标识符**，也不允许直接触碰 `document` / `window`。所有宿主能力经 platform adapter 注入（契约见 `docs/design.md` §2.3）。
2. `tools/lint-no-host-api.js` 在 CI 中静态检查这条约束，违反即构建失败。
3. **实现范围**：`platform/wx-minigame/`（发布形态）与 `platform/web/`（开发、单测、Playwright、CI）。这两个是 Stage 1–5 的全部工作量。
4. **保留范围**：`platform/wx-miniprogram/` 在规划的目录结构中保留位置（`docs/design.md` §4），标注为延后形态。当前不实现、不进 CI、不计入任何 Stage 的出口标准。
5. 主包体积目标 ≤2MB（`docs/design.md` §8）。主要理由是首屏加载速度；**同时它让第 4 条的延后选项保持可行**——一旦主包超出普通小程序的约束，「以后可以追加」就会在不知不觉中变成不可能。

第 1、2 条的正当性**主要来自 H5 宿主，而不是小程序宿主**：确定性回放、单元测试与 Playwright 截图都跑在 web 宿主上（`docs/design.md` §9、ADR 0001 §1），玩法层若耦合 `wx.*` 就无法在 Node 与浏览器里测试。因此即使延后选项将来被彻底放弃，这两条也不会放松。

## 理由

### 1. 动作射击的帧率与输入延迟要求，普通小程序架构满足不了

跑射游戏对帧时间抖动极其敏感：玩家一击死，一次 100ms 的卡顿可以直接造成非玩家过失的死亡。

普通小程序的逻辑层与渲染层是两个环境，中间隔着序列化通信。虽然 `<canvas type="2d">` 通过 `canvas.requestAnimationFrame` 减少了这层开销，但触摸事件仍要跨层送达逻辑层，帧循环也受组件生命周期与页面调度影响。**这条链路上的抖动不在我们的控制范围内**，无论怎样优化代码都无法保证。

小游戏形态是单一 JS 环境，直接持有 canvas，主循环由我们自己驱动——这正是 ADR 0001 里确定性定步长循环所需要的前提。

这也是为什么普通小程序只能是延后选项而不是并行目标：它在架构上就达不到同等手感。

### 2. 横屏是必需的，小游戏形态对它是一等支持

逻辑分辨率 256×224 的横版卷轴必须横屏运行（`docs/design.md` §5.1）。小游戏侧一行 `deviceOrientation: "landscape"` 即可；普通小程序的横屏支持要处理页面级配置与旋转时机，是持续的麻烦源。

### 3. 形态归属由项目方裁定，不由我们推断

初版 ADR 在这一点上是保守的：「小程序版本」这个措辞既可能指技术形态，也可能只是指分发渠道，而账号类目情况是我们无法单方面确定的因素，所以用架构对冲代替了猜测。

项目方已明确形态为小游戏，并明确保留普通小程序宿主这个选项。**需求方的直接裁定优于我们的任何推断**，包括优于我们对「对冲是否划算」的工程判断——保留选项的成本由项目方承担，是否值得由项目方决定。

### 4. 保留选项的成本很低，事后补救的成本很高

adapter 边界是无论如何都要有的——H5 宿主（开发与 CI 所需，见 ADR 0001）已经强制我们把宿主能力抽象出来。既然 adapter 已经存在且有 lint 强制，保留「将来可以加一个宿主」这个可能性的边际成本接近于零：不需要现在写任何代码，只需要不主动把 `wx.*` 泄进玩法层、以及不让主包膨胀到普通小程序装不下。

反过来，如果一开始就让 `wx.*` 渗进玩法层，事后要剥离等于重写；而这种渗透在没有 lint 强制时几乎必然发生。

## 被否方案

### 只做普通小程序（被否）

**优点**：最贴合原始措辞的字面读法；不需要游戏类目资质；账号申请门槛低。

**否决理由**：理由 1 的帧率与输入延迟风险是产品级的——一个卡顿的跑射游戏不是"稍差的版本"，而是不可玩的版本。另外它也会削弱确定性循环的基础。项目方确认目标是小游戏后，本方案的唯一支撑（字面措辞）也不再成立。

### 彻底删除普通小程序宿主的可能性（被否）

**优点**：规划里不留任何未实现的条目，文档与实际能力严格一一对应，没有「预留目录腐烂」的风险。

**否决理由**：项目方明确要求保留（「不删除」）。这不是工程权衡能覆盖的决定——保留一个未来形态的选项属于产品范围决策。本决策改为**用标注而不是删除来管理这个风险**：延后选项在文档中明确标为未实现、未验证，因此不会被误当成既有能力（见「后果」）。

### 两个形态同时作为一等公民并行开发（被否）

**优点**：两条路都不留遗憾。

**否决理由**：翻倍的真机测试矩阵与性能调优工作量，换来的是一个明确更差的版本也要达到"发布级"品质。在 MVP 阶段这是纯粹的浪费。项目方的「就只做微信小游戏」也直接排除了这个方案。

### 用 WebView 内嵌 H5（被否）

**优点**：一套 H5 代码通吃，开发成本最低。

**否决理由**：小程序 `web-view` 组件对个人主体不开放、需配置业务域名、无法使用小程序原生能力（分享、支付、订阅消息），且 WebView 内的性能与手感比 `<canvas type="2d">` 更不可控。同时它会让 §1 的问题变得更糟而不是更好。

## 后果

**接受的成本**：

- **游戏类目资质是发布前置条件**：小游戏必须以游戏类目的小程序账号提审。这不是需要架构对冲的设计风险（形态已定），但仍是 Stage 5 发布准备的检查项——代码完成不等于可发布。类目、备案，以及后续若加入付费或广告可能牵涉的版号，流程时间通常长于开发时间，应尽早启动。
- `engine/` 与 `game/` 里所有宿主能力都要走 adapter，写起来比直接调 `wx.*` 啰嗦一层。这是刻意的代价，由测试基建正当化。
- 主包 2MB 的目标限制了首关素材与代码规模，比小游戏平台的实际上限更紧。它同时服务首屏加载速度与延后选项的可行性。
- **延后选项是意图，不是已验证的能力。** `platform/wx-miniprogram/` 长期不实现、不进 CI，所以「随时可以追加」严格来说是一个基于 adapter 边界的合理预期，而非已证实的事实。缓解措施是：(a) lint 持续强制玩法层与宿主解耦；(b) 2MB 主包目标保持普通小程序的可装载性；(c) 文档明确标注其未实现状态，避免被后续 Step 当成现成能力引用。真正启用它时，第一件事应是做一次可运行验证，而不是假设它能跑。

**获得的收益**：

- 发布形态在帧率、输入延迟、横屏支持上都没有架构层面的天花板。
- 当前只有两个宿主要维护与验证，真机测试矩阵和 CI 都保持最小。
- adapter 边界有 lint 强制，两个已实现宿主共享同一套玩法代码，玩法行为逐帧一致；玩法层可在 Node 中直接单测。
- 普通小程序这条路保持开放，且开放的代价是持续的纪律（lint + 包体）而不是现在的工作量。

**重新评估的触发条件**：项目方要求启用普通小程序宿主（此时它从延后选项转为一个实现 Step，需先做可运行验证）；游戏类目资质确认不可得；或微信平台改变两种形态的能力边界（例如普通小程序获得等价的主循环控制权）。
