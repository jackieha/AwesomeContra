# AwesomeContra 设计文档

项目代号 **AwesomeContra**，一款横版跑射（run-and-gun）像素动作游戏，主形态为**微信小游戏**，架构上同时保留普通微信小程序宿主与 H5 宿主。

本文件是全项目的**单一规范来源**。数据文件格式见 `docs/formats.md`，调色板见 `docs/palette.json`，两个关键技术决策见 `docs/adr/`。任何实现与本文冲突时，先改本文再改代码。

---

## 1. 合规前提（硬约束）

这是一款**风格致敬作**，不是移植、不是复刻数据。以下是不可协商的红线：

- **不使用任何 Konami 原版资产**：不复用原版精灵图、背景图、音乐、音效、字体、关卡数据，不使用 ROM 提取物或从 ROM 反推的图块/坐标表。
- 所有像素素材由本项目自制（`tools/` 下的生成脚本 + 手绘），统一约束在 `docs/palette.json` 的 24 色内。
- 所有关卡编排为原创，不按原版关卡逐段还原。
- 玩法机制本身是通用的游戏设计语汇（横版卷轴、8 向瞄准、字母武器道具、一击死），可以自由借鉴。
- **对外游戏标题不使用「魂斗罗 / Contra」**。代码仓库名沿用既有的 `AwesomeContra`；发布用标题在 Stage 5 单独确定。
- 标题页与 README 需带致敬声明：非 Konami 官方作品、与 Konami 无关联、素材全部自制。

评审任何 PR 时，「引入了来源不明的图片/音频」是直接拒绝的理由。

## 2. 项目形态与三宿主架构

### 2.1 为什么主形态是小游戏

动作射击要求稳定 60fps 与一个由自己掌控的主循环。微信小游戏形态提供 `wx.createCanvas()` 与 `requestAnimationFrame`，是唯一能满足这一点的宿主；普通小程序的 `<canvas type="2d">` 走组件与逻辑层-渲染层通信，帧率与输入延迟都不可控到同等程度。

详细取舍见 `docs/adr/0002-minigame-vs-miniprogram.md`。

### 2.2 三宿主

| 宿主 | 目录 | 角色 | 何时用 |
|---|---|---|---|
| 微信小游戏 | `platform/wx-minigame/` | **发布形态** | 真机验证、发布 |
| H5 / 浏览器 | `platform/web/` | **开发与自动化形态** | 日常开发、单测、Playwright 截图、CI |
| 微信小程序 | `platform/wx-miniprogram/` | 备用形态（Stage 5 之后按需） | 需要「普通小程序」字面形态时 |

### 2.3 Platform Adapter 契约

`engine/` 与 `game/` **不允许出现任何 `wx.` 前缀的标识符**，也不允许直接触碰 `document` / `window`。所有宿主能力经一个 adapter 对象注入，由 `tools/lint-no-host-api.js` 在 CI 中静态检查。

```js
// platform adapter 契约（platform/<host>/index.js 默认导出）
{
  canvas,                    // 一个具备 getContext('2d') 的对象
  dpr,                       // number，设备像素比
  screen: { w, h },          // 物理像素尺寸
  now(),                     // ms，单调递增时钟
  raf(cb), cancelRaf(id),
  loadImage(path),           // -> Promise<ImageLike>
  loadJSON(path),            // -> Promise<object>
  loadAudio(path),           // -> Promise<AudioLike>
  input: {                   // 由宿主翻译成统一事件
    onPointer(cb),           // cb({ id, phase:'down'|'move'|'up', x, y })  x/y 为物理像素
    onKey(cb),               // 仅 web 宿主实现；其余宿主传 noop
  },
  storage: { get(k), set(k, v) },
  vibrate(ms),               // 无能力宿主传 noop
  safeArea: { top, right, bottom, left },  // 物理像素
}
```

规则：**任何 adapter 能力缺失时必须降级为 noop 而不是抛错**。宿主差异只允许体现在触感与音频这类非玩法维度上——玩法层的行为在三个宿主上必须逐帧一致。

## 3. 引擎选型

**自研极简 Canvas 2D 引擎**，零运行时依赖，不使用 Cocos Creator / LayaAir / Egret。

四条理由（完整论证与被否方案见 `docs/adr/0001-engine-choice.md`）：

1. 本项目全程由 agent 以纯文本代码推进。编辑器驱动的工程会产生二进制场景文件与 GUI 资源绑定，无法可靠地被增量修改和 code review。
2. 2D 像素横版射击不需要商业引擎的重型能力（3D、刚体物理、动画状态机编辑器）。引入它们只是把包体和不可控行为一起引入。
3. 包体预算下（§8），零运行时依赖是显著优势。
4. **只有自研内核能保证确定性定步长模拟**，而确定性是 §9 自动化回归测试的前提。这是最关键的一条。

## 5. 显示规范

### 5.1 逻辑分辨率与缩放

- **逻辑分辨率固定 `256 × 224`**（NES 风格；NES 可见区为 256×240，224 是各机型都安全的高度）。所有玩法坐标、碰撞、摄像机都在这个坐标系里，与屏幕无关。
- **只做整数倍缩放**，剩余空间 letterbox / pillarbox 填 `void` 黑。
- `ctx.imageSmoothingEnabled = false`，且 `ctx.setTransform` 只使用整数平移与整数缩放——**绝不允许非整数的绘制坐标**，否则像素会被重采样出毛边。
- **强制横屏**：小游戏侧 `game.json` 内 `deviceOrientation: "landscape"`。

缩放系数必须在**物理像素**上计算，不是 CSS 像素。这是最容易踩的坑：一台 375×812 CSS 像素、dpr=3 的手机横屏后 CSS 尺寸是 812×375，`floor(375/224) = 1`，会得到 1 倍缩放这种荒谬结果；换算到物理像素 2436×1125 后 `floor(1125/224) = 5`，才是正确答案。

```js
// engine/renderer.js
const LOGICAL_W = 256, LOGICAL_H = 224;
function computeScale(screenPhysicalW, screenPhysicalH) {
  return Math.max(1, Math.floor(Math.min(screenPhysicalW / LOGICAL_W,
                                         screenPhysicalH / LOGICAL_H)));
}
// 画布 backing store 设为 screenPhysical*，居中放置 256*scale × 224*scale 的视口
```

8:7 的逻辑画幅放到 16:9 屏幕上必然左右留黑。这是刻意接受的：横向扩宽视野会让玩家提前看到更多敌人，直接改变难度曲线。左右留黑区在 Stage 5 用装饰边框填充。

### 5.2 素材规格

| 对象 | 尺寸 | 备注 |
|---|---|---|
| tile | 16 × 16 | 关卡地形与装饰的唯一单位 |
| 玩家 站/跑/跳 | 16 × 24 | 碰撞盒比精灵窄，见 §6.2 |
| 玩家 卧倒 | 24 × 12 | 变矮变宽，用于钻过低矮空隙 |
| 步兵类敌人 | 16 × 24 | |
| 炮台 | 24 × 24 | |
| 子弹 | 4 × 4 ~ 8 × 8 | 激光 16 × 4 |
| 道具胶囊 | 16 × 12 | 字母图标 8 × 8 |
| Boss（关底墙面） | 96 × 128 | 拆成多个部件分别绘制与受击 |
| HUD 字形 | 8 × 8 | 仅 `0-9 A-Z` + 少量符号 |

### 5.3 美术约束

- 全项目共用 `docs/palette.json` 的 24 色，`tools/lint-palette.js` 在 CI 强制校验；alpha 只允许 0 或 255（不存在半透明像素）。
- 角色与可交互物件用 `void` 描边 1px；背景装饰不描边，靠明度分离。
- 每个材质用 3 阶明暗（见 palette 的 `ramps`）。光源统一从左上。
- 玩家 2 通过调色板换色实现（`ramps.player2`），不做第二套素材。

### 5.4 安全区与虚拟按键

HUD 与虚拟按键锚点按 adapter 提供的 `safeArea` 避让刘海与手势条。虚拟按键**不参与整数缩放**——它们绘制在物理像素层，尺寸按实际毫米感受调，不能随逻辑分辨率一起被放大成巨型方块。

布局：左手侧 8 向虚拟摇杆（自由触摸区，非固定圆盘），右手侧 `射击` / `跳跃` 两枚按钮 + 长按射击自动连发。触摸区域比可见图形大 ~1.3 倍。

## 6. 玩法机制细则

### 6.1 范围

**MVP（Stage 1–4 交付）**：单人、第 1 关「丛林」完整可通关 + 关底 Boss。

**Stage 5 及之后（范围外，需确认后才做）**：双人合作、纵版/基地关、排行榜与分享、更多关卡。

### 6.2 玩家

碰撞盒与精灵尺寸分离——这是手感的关键。精灵 16×24，**碰撞盒 10×22**（居中，左右各留 3px 余量），卧倒时 20×10。玩家判定"被击中"用一个更小的 6×14 命中盒，让擦身而过的子弹不算命中。

状态机：

```
        ┌──────────────────── jump ────────────────────┐
        │                                              ▼
  ┌──────────┐  →dir  ┌──────────┐   ground lost   ┌──────────┐
  │  STAND   │ ⇄      │   RUN    │ ──────────────→ │   AIR    │
  └──────────┘        └──────────┘                 └──────────┘
     │   ▲                                            │  │
  down│  │up                                    land  │  │ down+jump（在单向平台上）
     ▼   │                                            ▼  ▼
  ┌──────────┐                                   ┌──────────┐
  │  PRONE   │                                   │ DROP-THRU│（1 帧，忽略 oneway）
  └──────────┘                                   └──────────┘

  任意状态 ── 进入水域 ──→ WATER（半身，见 6.6）
  任意状态 ── 被击中 ────→ DEAD ──→ RESPAWN（无敌闪烁）──→ STAND
```

- **跑**：无加速度斜坡，按下即达全速。跑射时不减速（与部分同类作不同——这里选择不减速，因为触屏操作已经比手柄迟钝，再加惩罚会难受）。
- **跳**：定高跳，不做"松手即降"的可变跳高（原作即是定高跳）。空中不可二段跳，可微调水平方向。
- **穿越单向平台**：向上跳可从下方穿过 `oneway` tile；`下 + 跳` 触发 `DROP-THRU`，1 帧内忽略 `oneway` 碰撞后落下。
- **卧倒**：变矮，只能向前射，水平速度 0。
- **一击死**：任何敌方伤害都致死，无血量。3 命，命尽 game over。
- **复活**：原地复活，无敌 2s（120 帧）并以 4 帧周期闪烁；无敌期间不受伤害但仍可被地形推动。武器退回默认步枪 `N`。

### 6.3 8 向瞄准

| 状态 | 可用方向 |
|---|---|
| STAND | 上、斜上、前 |
| RUN | 上、斜上、前（斜上为跑射时的默认抬枪角） |
| PRONE | 前（低位） |
| AIR | 上、斜上、前、斜下、下 |
| WATER | 上、斜上、前 |

方向由输入位掩码直接映射，无瞄准惯性。空中按住 `下` 且无左右输入 → 垂直向下射（原作的经典机制）。

### 6.4 物理基线

见 §11 常量表。核心：AABB + 单向平台 + 水域体积，无旋转、无斜坡（第 1 关不含斜坡；若后续关卡需要，作为独立 Step 引入）。

碰撞求解顺序固定：**先积分 y、解 y 轴碰撞，再积分 x、解 x 轴碰撞**。顺序固定是确定性的一部分，不允许按情况调整。

### 6.5 武器

字母道具，6 种 + 屏障。切换即替换（不叠加），死亡退回 `N`。

| 键 | 名称 | 弹速 px/s | 冷却帧 | 屏上限 | 伤害 | 行为 |
|---|---|---|---|---|---|---|
| `N` | 步枪 Rifle | 300 | 8 | 5 | 1 | 单发直线；点射 |
| `M` | 机枪 Machine Gun | 300 | 5 | 8 | 1 | 按住连发 |
| `F` | 火焰弹 Fire | 200 | 12 | 4 | 1 | 沿前进方向做半径 8px、周期 20 帧的螺旋 |
| `S` | 散弹 Spread | 280 | 14 | 15 | 1 | 每次 5 发，扇形 ±24°（间隔 12°） |
| `L` | 激光 Laser | 480 | 20 | 2 | 3 | 贯穿；命中不消失，可穿透多个敌人 |
| `R` | 追踪 Homing | 240 | 10 | 6 | 1 | 发射后以 180°/s 转向最近敌人 |
| `B` | 屏障 Barrier | — | — | — | — | 10s（600 帧）无敌，不改变当前武器 |

- 屏上限达到后射击输入被丢弃（不排队）。
- 子弹离开摄像机视野外 32px 即回收。
- 载体两种：**横向飞过的胶囊**（沿固定高度匀速飞过，被击中后掉落字母道具）与**固定发射台**（地面装置，击破后弹出道具）。
- 道具字母在地面停留 480 帧后消失，消失前 120 帧加速闪烁。

### 6.6 水域

进入 `water` 体积后：玩家下沉至半身（视觉上截去下半），碰撞盒改为 10×12 并贴附水面高度，移动速度降为 `RUN_SPEED * 0.6`，**不能跳跃**，瞄准方向受限为 上/斜上/前，无法卧倒。离开水域立即恢复。

### 6.7 敌人

| id | 名称 | HP | 速度 | 行为 | 分值 |
|---|---|---|---|---|---|
| `runner` | 跑步兵 | 1 | 60 | 朝玩家方向直跑，不射击，触碰致死 | 100 |
| `cover` | 掩体兵 | 1 | 0 | 蹲在掩体后，每 90 帧朝玩家当前位置射 1 发（弹速 180） | 200 |
| `grenadier` | 投弹兵 | 1 | 30 | 每 120 帧抛物线投弹（初速 120, -240），落地爆炸半径 20px | 300 |
| `turret` | 旋转炮台 | 3 | 0 | 8 向扫射，每 45 帧 1 发；受击闪白 | 500 |
| `frogman` | 水中蛙人 | 1 | 40 | 水下潜行，每 100 帧上浮射 1 发后下潜 | 200 |
| `bridge_guard` | 桥上守卫 | 1 | 45 | 边退边射，桥段爆破时随桥坠落 | 150 |

所有敌人由 **spawner** 按摄像机 x 触发：tilemap 里放置 `spawn` 实体点，摄像机右边缘越过该点 x 时生成，离开视野左侧 48px 后回收。同屏敌人上限 12，超限的 spawner 延后触发而非丢弃。

### 6.8 关卡 1「丛林」段落

```
[0]  卷轴推进段     地面 + 单向平台 + 掩体兵/跑步兵混编，教学式难度
[1]  桥梁爆破段     多跨桥面；投弹兵在对岸；击破桥墩使桥段依次坠落，守卫随桥落水
[2]  水域段         齐腰河道，蛙人从水下上浮；岸上炮台压制
[3]  关底墙面 Boss  屏幕停止卷轴，正面墙体
```

**Boss**：墙面结构，三个可独立受击部件——左炮口（HP 8）、右炮口（HP 8）、中央核心（HP 12）。炮口每 60 帧射 3 向散射；两炮口都被破坏后核心暴露，核心射速加倍。核心被破 → 全屏爆炸序列 → 过关结算。分值 10000。

Boss 战限时 90s；超时不是失败，但会额外增派 `runner`。

### 6.9 HUD 与计分

- 左上：命数（图标 × N）、当前武器字母。
- 右上：得分（7 位）。
- 分值见 §6.7；胶囊击破 500，道具拾取 0（价值在武器本身）。
- **1UP**：20000 分首次，之后每 50000 分。
- 无关卡计时显示。

## 7. 数据与资源

所有关卡、图集、武器表、敌人表都是**外部数据文件**，不是硬编码常量。格式规范与完整可复制示例见 `docs/formats.md`：

- tilemap JSON —— 图层、tile 索引、碰撞类型（`solid` / `oneway` / `water`）、实体放置点
- 图集 JSON —— frame 名、xywh、锚点、动画序列与每帧时长
- 武器表 / 敌人表字段
- 输入回放格式 —— `{ seed, frames: [[frame, inputBitmask], ...], checksum }`

数据文件在加载时用 `tools/validate-level.js` 的同一套 schema 校验；**校验失败必须硬失败**，不允许静默使用默认值——静默降级会让一个坏关卡表现为"手感突然不对"，极难定位。

## 8. 性能预算

| 指标 | 预算 | 如何验证 |
|---|---|---|
| 帧率 | 60fps 稳定 | 真机抽检 + web 宿主帧时间直方图 |
| 逻辑帧耗时 | **< 8ms**（目标 < 4ms） | `tests/perf/` 基准，超阈值 CI 失败 |
| 渲染帧耗时 | < 6ms | 同上 |
| `drawImage` 调用 | **< 300 / 帧** | renderer 内置计数器，dev 模式下超限告警 |
| 游戏内堆分配 | **零** | 见下 |
| 同屏实体 | 子弹 64、敌人 12、特效 32 | 对象池容量即硬上限 |
| 主包 | **≤ 2MB**（代码 + 首关图集） | CI 打包后体积断言 |

**零堆分配**是硬规则：`game/` 与 `engine/` 的每帧执行路径中禁止 `new`、数组/对象字面量、闭包创建、`Array.prototype.map/filter/forEach`、字符串拼接。所有实体从 `engine/pool.js` 借还，向量运算写进预分配的 out 参数。原因是移动端 GC 停顿会直接表现为掉帧尖峰，而跑射游戏对帧时间抖动极其敏感。启动与关卡加载阶段不受此限制。

包体：音频与第 2 关起的资源走分包。**2MB 是一个刻意保守的目标**，不是平台硬限——它同时满足普通小程序宿主的主包约束，从而让 §2.2 的备用形态一直可行。发布前需按微信最新官方文档复核当期的主包/总包上限。

## 9. 测试与验证策略

这一节是本项目能被 agent 可靠推进的前提，优先级等同于玩法本身。

### 9.1 单元测试（Node + vitest）

物理积分、AABB 与单向平台碰撞、玩家状态机迁移、武器弹幕生成、伤害结算、摄像机边界钳制、计分与 1UP 阈值——全部写成不依赖宿主的纯函数，直接在 Node 里测。

### 9.2 确定性回放回归（核心手段）

前提：固定 1/60 步长；唯一随机源是 `engine/rng.js` 的显式播种 PRNG；不读挂钟时间；碰撞求解顺序固定；遍历顺序稳定（不依赖对象键序）。

做法：录制 `(frame, inputBitmask)` 序列与末态校验和（玩家位置、命数、得分、存活实体计数的哈希），CI 回放比对。任何改动破坏既有时序或手感，都会在这一层显形——**这是唯一能自动捕获"手感回归"的机制**，比截图和单测都关键。

回放用例分两类：`tests/replay/spec/`（人工设计的机制断言，如"从这个位置起跳恰好落在平台上"）与 `tests/replay/session/`（完整通关录像）。

### 9.3 H5 宿主 + Playwright

视觉回归截图，以及"真的能跑起来"的端到端验证。截图在固定帧号（回放驱动）截取，保证可比对。

### 9.4 真机

微信开发者工具 + iOS/Android 各一台，抽检帧率、触控手感、安全区适配。真机是**唯一**能验证触屏手感的手段，不能被自动化替代——每个 Stage 出口都必须过一次真机。

## 12. 与 LEDA-1 初始方案的差异记录

LEDA-1 方案中的六个关键常量全部**原样保留**：重力 900、跳跃初速 320、跑速 90、逻辑分辨率 256×224、tile 16、主包 ≤2MB。以下是本文在实现层面做的补充与澄清，均为增量，不推翻原方案：

1. **新增 `MAX_FALL_SPEED = 420`（原方案未指定下落速度上限）。**
   理由是正确性而非手感：重力 900 无上限时，下落约 1s 后速度达 900px/s，即 **15px/帧**，已逼近 16px 的 tile 尺寸；再高就会在一帧内跨过整块 tile，导致穿地。420px/s = 7px/帧，为 tile 尺寸的 44%，让"每帧位移小于 tile 尺寸"这个前提成立，从而允许用简单的逐轴 AABB 求解而不必写扫掠碰撞（swept collision）。手感上 420 对应约 1.4 tile/帧的坠落观感，与原作接近。

2. **明确碰撞盒与精灵尺寸分离**（原方案只给了精灵尺寸 16×24）。增加 `PLAYER_BOX` 10×22 与更小的 `PLAYER_HURTBOX` 6×14。跑射游戏的公平感几乎全部来自受击盒比视觉体积小。

3. **明确缩放系数必须在物理像素上计算**（原方案只写了"整数倍缩放"）。见 §5.1 的反例——在 CSS 像素上算会得到 1 倍缩放。

4. **明确 2MB 是保守目标而非平台硬限**，其作用是保持普通小程序宿主形态一直可行；当期平台上限需在发布前按官方文档复核。

5. **补齐原方案标为"可调"的数值**：下落上限、无敌时长与闪烁周期、摄像机死区与跟随速度、道具存活时长、各武器冷却与屏上限、各敌人 HP/速度/攻击间隔、分值与 1UP 阈值。这些是 Stage 2–3 实现时必须有确定值才能写测试的量，此处给出首版取值；调整时改本文的 §11 与 §6，不在代码里就地改。

6. **明确第 1 关不含斜坡**，斜坡若需要则作为独立 Step 引入。原方案未提及斜坡，而"AABB 无斜坡"是个影响关卡设计的重要边界，需要写明。

7. **明确数据校验失败必须硬失败**（§7），不允许静默默认值。
